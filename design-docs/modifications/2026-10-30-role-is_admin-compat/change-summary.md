# 域名切换后登录提示「当前url非法」：问题说明与处理

> 日期：2026-10-30 ｜ 涉及：控制台前端（`ai-gateway-web`）；控制面接口本次不改
> 状态：前端代码已改完并验证，随下一个版本发布

## 一、一句话结论

0.11 把登录返回里“是否管理员”的字段换成了“角色”字段；切换域名后浏览器还在跑 0.10 的旧前端，旧前端只认老字段，拿不到就当“不是管理员”，于是把每个登录成功的人都挡在门外，并提示了一句和 URL 无关的「当前url非法」。

## 二、事情是怎么发生的

1. A 环境部署的是 0.10 版本（前端和后端都是 0.10），域名解析指向 A，大家一直正常使用。
2. 后来搭了 B 环境，是 0.11 版本（前端和后端都是 0.11）。
3. 运维只改了域名的解析，把它指向 B —— **域名没变，只是它背后的服务器换了**。
4. 用户还从这个域名登录，进去就弹「当前url非法」，点确定回到登录页，反复登录都一样。

## 三、为什么：管理员身份的表达方式变了

### 3.1 老版本（0.10）用“是否管理员”表示

登录接口返回一个布尔字段 `is_admin`（true / false）。前端判断非常直接：不是管理员就拒绝进入控制台。当时能登录的账号 `is_admin` 都是 true，所以一切正常。

### 3.2 新版本（0.11）改用“角色”表示

0.11 起 `is_admin` 被废弃，改成枚举字段 `role`，只有两个取值：

| `role` 取值 | 含义 |
| --- | --- |
| `system_admin` | 系统管理员 |
| `system_admin_readonly` | 系统管理员（只读） |

登录响应里**不再返回 `is_admin`**，只返回 `role`。

### 3.3 于是旧前端必然误判

旧前端只会去找 `is_admin`。新后端不发这个字段，它拿到的就是“空”，而“空”在旧代码里等同于“不是管理员” → 拒绝所有账号，包括真正的管理员。

注意：**登录本身是成功的**（接口返回 200，会话也建好了），失败发生在登录之后的页面校验，所以表现为“登录成功却提示非法”。

| 组合 | 登录接口返回 | 前端判定结果 |
| --- | --- | --- |
| 0.10 前端 + 0.10 后端 | `is_admin: true/false` | 正常 |
| 0.11 前端 + 0.11 后端 | `role` | 正常 |

### 3.4 新前端读取旧登录状态时的规则

- 有 `role` → 按 `role` 放行；
- 没有 `role`、但 `is_admin` 为 **true**（升级前存下的）→ 视为系统管理员放行；
- 没有 `role`、`is_admin` 为 **false**（升级前存下的普通账号）→ 仍然拒绝（**不**降级成“只读管理员”，否则等于把普通账号自动放行成能读控制台）；
- 两个字段都没有 → 判定为“前后端版本不一致”，给出对应提示。

用一句话概括：**`role` 优先，缺失时用 `is_admin` 兜底，但只认 `is_admin = true`。**

### 3.5 让这个问题真的发生的两个条件

- **浏览器还在跑旧程序**：域名没变，浏览器认为还是原来那个网站，继续用缓存的旧页面；服务端当时也没告诉浏览器“文件更新了要重新取”。所以用户眼里是“新地址”，实际执行的是 0.10 的前端。
- **本地还留着旧登录状态**：浏览器里存的是旧格式的登录信息（只有“是否管理员”）。即使加载了新前端，一进页面也会被这份旧数据判成不可用。

### 3.6 放大器：提示文案说错了方向

「当前url非法」让人以为是域名或地址写错了，实际上和 URL 没有任何关系，也没有告诉用户下一步该做什么。

## 四、怎么快速判断属于哪一种

| 看到的现象 | 实际原因 | 怎么处理 |
| --- | --- | --- |
| 打开页面、还没点登录就弹「URL 非法」 | 浏览器里留着旧格式的登录状态（只有 `is_admin`） | 清除该站点的本地数据；本次改动已能让它自动兼容 |
| 点了登录、每次都弹「URL 非法」 | 浏览器还在跑 0.10 的旧前端，拿不到 `role` | 用户在浏览器里强制刷新一次（本次不改后端缓存策略，无法替他刷新） |
| 提示「Session Key 错误 / 登录已过期」 | 本地存的是 A 环境的会话，B 环境不认 | 重新登录即可，属于正常现象 |

## 五、我们改了什么

### 前端（控制台）

- **兼容旧登录状态**：浏览器里留着的旧格式登录信息（只有 `is_admin`）在读取时自动补出对应角色：`true` 视为系统管理员、`false` 仍然拒绝（不降级为只读），打开页面不再一上来就被拦。
- **提示改成能看懂、能照做的两句话**：
  - 前后端版本对不上（`role` 和 `is_admin` 都没有）时，提示“版本不一致，请强制刷新后重试；仍不行请联系管理员升级到同一版本”，点确定会重新加载页面，而不是无效地跳回登录页；
  - 确实没有权限（如 `is_admin = false`）时，提示“控制台只支持系统管理员，请用管理员账号登录或联系管理员调整角色”，点确定回登录页。
- 「当前url非法」这句话已经删除。
- **两处兜底，避免“卡住不动”**：
  - 浏览器里的登录数据损坏、读不出来时，自动丢弃并按“未登录”处理，回到登录页，不会每次跳转都报错；
  - 拉取导航菜单失败（网络或接口异常）时，不再中断页面跳转，页面照常打开（菜单可能为空），权限仍由服务端接口把关。

> 后端（控制面）本次不做改动：浏览器缓存旧页面这件事，只能靠用户强制刷新一次解决；后续若要根治，需要后端配合给静态资源加缓存策略，另行排期。

## 六、改完之后用户会看到什么

| 场景 | 用户看到 |
| --- | --- |
| 正常的新版本环境 | 和以前一样，登录后直接进首页 |
| 前后端版本确实对不上（两个字段都没有） | 一句“版本不一致 + 强制刷新”的提示，点确定重新加载页面 |
| 账号确实没有控制台权限（旧格式记录里 `is_admin = false`） | 一句“只支持系统管理员”的提示，点确定回登录页 |
| 浏览器还留着旧登录状态 | 不再被误拦；如果是旧环境的会话，会提示重新登录 |

## 七、验证情况

- 前端代码检查与打包通过（本次仅前端改动，后端未动）。
- 在浏览器里把登录状态改造成四种形态逐一实测：只有 `is_admin = true`、只有 `is_admin = false`、两个字段都没有、正常 `role`。四种表现都与上表一致。
- 两个边界也实测过：① 把浏览器里的登录数据改成非法内容 → 提示“请先登录”，点确定回到登录页；② 让菜单接口返回错误 → 页面照常打开（菜单为空），不会被弹回登录页或白屏。
- 以上五种情况已固化为自动化用例：`ai-gateway-web-test/tests/user/test_14_login_state_compat.spec.js`（UM-34～UM-38），与登录用例同轮执行 8/8 通过。

## 八、上线注意

1. **前后端按同一版本配套发布**。
2. **切换环境时**，确认新地址上的页面文件是整体替换的，不要只替换一部分。
3. **升级后通知用户强制刷新一次**：浏览器缓存的旧页面只能由用户端刷新（`Ctrl/Cmd+Shift+R`），服务端本次未做缓存策略，无法代劳；浏览器里残留的旧登录状态已由前端自动兼容，无需额外清理。
4. **回滚**：前端、后端、页面文件按同一版本整体回滚，不要只回滚其中一部分。

## 九、后续建议

- **给静态资源加缓存策略**（需后端配合，本次未做）：让首页和主程序每次回源校验，可彻底避免“升级/切环境后仍跑旧页面”，也就不再需要每次通知用户强刷。
- **给登录状态加版本号**：以后字段再变化时，读到不认识的格式就直接要求重新登录，而不是让整个控制台不可用。
- **发布时自动比对前后端版本**：不一致就提前提示，不要等用户登录了才发现。
- **文案规范**：错误提示不能只写“url非法/未知错误”这类没有主语、没有下一步的说法，至少要写清“是什么问题 + 该怎么做”。
